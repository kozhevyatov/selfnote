# SelfNote — сервис заметок и задач

Этот файл — главное описание проекта для агентов (Codex и т. п.) и людей.
Читай его целиком перед началом работы. Язык интерфейса и комментариев — русский.

---

## 1. Что это

Self-hosted сервис заметок и задач. Работает в Docker на домашнем Synology владельца.
С первого дня проектируется под мобильные приложения: сначала веб + PWA, потом
нативное приложение (Expo / React Native).

Ключевые идеи:

- **Заметки и задачи — одно целое.** Задача — это пункт чек-листа внутри заметки.
  Отдельная вкладка «Задачи» собирает пункты из всех заметок.
- **Local-first / серьёзный офлайн.** Основная база живёт на устройстве. Сервер —
  точка синхронизации и бэкап. Без сети можно всё: создавать, править, отмечать задачи.
- **История изменений** у каждой заметки с откатом.
- **Шаринг** по публичной ссылке (с паролем и сроком жизни) и **совместное
  редактирование** по персональной ссылке + PIN.
- **Пароль на саму заметку** — настоящее шифрование на клиенте (сервер не может прочитать).

## 2. Функции

### 2.1. Организация

- **Записные книжки** (notebooks) → **подразделы** (один уровень вложенности).
  Пример: книжка «Радио DFM» → подразделы «Эфиры», «Конкурсы».
  Заметка лежит в книжке и, опционально, в одном подразделе.
- **Метки** (теги) — сколько угодно на заметку, плоский список (`#важное`, `#идеи`).
- Закрепление заметки (pinned), корзина (soft delete, автоочистка через 30 дней).
- Системные разделы: «Все заметки», «Задачи», «Общие» (расшаренные/совместные), «Корзина».

### 2.2. Редактор

Простой WYSIWYG на TipTap:

- жирный, курсив, зачёркнутый;
- **скрытый текст (спойлер)** — своя марка, показывается по клику;
- ссылка, заголовок (H2/H3), маркированный и нумерованный список;
- **чек-лист** (задачи) — см. 2.3;
- вставка картинок (загрузка, вставка из буфера, drag & drop);
- автосохранение, никаких кнопок «Сохранить».

Документ хранится **как Yjs-документ** (не HTML). Для поиска/рендера сервер
извлекает plain text и структуру.

### 2.3. Задачи

- Пункт чек-листа (`taskItem`) с атрибутами: `id` (uuid), `checked`, `due`
  (дата `YYYY-MM-DD` или дата-время ISO с часовым поясом), `doneAt`.
- Чип срока у задачи: «Сегодня» (акцент), «Просрочено · 12 ноя» (красный), дата (серый).
- Вкладка «Задачи»: «Сегодня», «Просрочено», «Предстоящие», «Без срока».
  Отметка во вкладке меняет пункт внутри заметки (и наоборот).
- Позже: повторы (RRULE), напоминания (Web Push / локальные уведомления в приложении).

### 2.4. История версий

- Снапшот версии: раз в 5 минут активного редактирования, при закрытии заметки,
  вручную («Сохранить версию»).
- Храним целый снапшот (`Y.encodeStateAsUpdate`), не диффы. Дифф считается только для показа.
- Прореживание: всё за последние 24 ч → по одной в день за 30 дней → по одной в неделю.
- Восстановление = новая версия с содержимым старой (история не теряется).
- У версии хранится автор (пользователь или гость совместного редактирования).

### 2.5. Пароль на заметку (шифрование)

- Шифрование **на клиенте**: AES-GCM 256 (WebCrypto), ключ из пароля через
  argon2id (`hash-wasm`), соль и параметры хранятся рядом с шифром.
- Сервер хранит только непрозрачный зашифрованный блоб + метаданные (заголовок можно
  тоже зашифровать — опция).
- Синхронизация зашифрованной заметки: клиент шифрует весь снапшот Y.Doc и отправляет
  блоб через REST с номером версии (last-write-wins; при конфликте — копия
  «(конфликт)»). Совместное редактирование зашифрованных заметок **не поддерживается**.
- Задачи из зашифрованной заметки сервер не видит: вкладка «Задачи» и поиск по ним
  работают на клиенте после разблокировки; напоминания — только локальные.
- Забыл пароль → заметку не восстановить. Это явно пишем в интерфейсе.

### 2.6. Публичные ссылки

- Таблица `shares`: случайный токен (32 байта, base64url), режим «только чтение»,
  необязательный пароль ссылки (argon2id-хеш на сервере), срок жизни, отзыв.
- Публичная страница `/s/<token>` рендерится сервером (OG-превью для Telegram).
- Картинки в расшаренной заметке отдаются по тому же токену.
- Зашифрованная заметка: ключ кладётся во фрагмент ссылки `/s/<token>#<key>`
  (не уходит на сервер). Если у ссылки есть пароль — ключ заметки оборачивается
  ключом, выведенным из пароля ссылки. Пароль заметки и пароль ссылки — разные.

### 2.7. Совместное редактирование

- Зарегистрированным пользователям сервиса — по приглашению (роли: владелец / редактор / читатель).
- Гостям — **персональная ссылка + PIN** (≥ 6 символов):
  - 5 неверных попыток → блокировка ссылки на 1 час;
  - при входе гость вводит имя (оно идёт в историю версий);
  - срок жизни, лимит устройств, отзыв конкретной ссылки;
  - гостям ограничена загрузка файлов (размер/количество, или запрет).
- Realtime через Yjs + Hocuspocus (курсоры и присутствие — «Дима редактирует»).

### 2.8. Аккаунты

- Мастер первого запуска (как в других проектах владельца): выбор БД (SQLite или
  существующая MariaDB), создание администратора, регистрация открыта/закрыта/по приглашению.
- Пароли: argon2id. Rate limit на логин.
- Токены: короткий access JWT (15 мин) + refresh-токен (веб — httpOnly cookie,
  приложение — secure storage). Список сессий с «выйти на этом устройстве».

### 2.9. Картинки и файлы

- Загрузка через REST, лимит 20 МБ, хранение `data/attachments/<userId>/<sha256>.<ext>`.
- `sharp`: превью, удаление EXIF (геолокация!).
- Отдача только через бэкенд с проверкой прав (или share-токена). Офлайн: картинка
  кладётся в IndexedDB и загружается при появлении сети.

### 2.10. Поиск

- Клиент: MiniSearch по локальной базе (работает офлайн).
- Сервер: MariaDB `FULLTEXT` / SQLite FTS5 по извлечённому `plain_text` (не для зашифрованных).

## 3. Архитектура и стек

```
Браузер / PWA / (позже) Expo
 ├─ React + TipTap + Yjs
 ├─ y-indexeddb  — локальное хранилище (офлайн)
 └─ HocuspocusProvider (WebSocket) ─┐
                                    ▼
Docker-контейнер selfnote (Node.js)
 ├─ Fastify: REST API (auth, setup, shares, uploads, versions, tasks, search)
 ├─ Hocuspocus: синхронизация Yjs по WebSocket на /collab
 ├─ отдаёт собранный фронтенд (статикой) и публичные страницы /s/:token
 └─ Kysely → SQLite (файл в data/) или MariaDB (сеть db)
```

| Монорепо | npm workspaces |
| Фронтенд | React 19, Vite, TipTap (+ Collaboration, TaskList/TaskItem, Link, Image, свой Spoiler mark), Zustand для UI-состояния |

| Крипто | WebCrypto AES-GCM, hash-wasm (argon2id) на клиенте; argon2 на сервере |

| Тесты | Vitest (особенно: синк, извлечение задач/текста из Yjs, шифрование) |

### 3.1. Модель синхронизации

- **Документ пространства пользователя** (`space:<userId>`, один Y.Doc): дерево
  книжек и подразделов, метки, метаданные заметок (title, notebookId, sectionId,
  tags, pinned, updatedAt, deletedAt, encrypted, color). Метаданные каждой заметки —
  **`Y.Map` по полям** (`notes.<id>.<поле>`), чтобы офлайн-правки разных полей на
  разных устройствах не затирали друг друга. Старый формат (целый объект) ещё
  встречается и переводится в `Y.Map` при первом изменении — читать нужно оба.
- **Документ заметки** (`note:<noteId>`, отдельный Y.Doc): `Y.XmlFragment('content')`
  для TipTap Collaboration.
- UUID всего генерирует клиент (можно создавать офлайн) — только через `uuid()` из
  `apps/web/src/ids.ts` (работает и без HTTPS). `crypto.randomUUID` напрямую не использовать.
- Все документы синхронизируются через **одно** WebSocket-соединение
  (`HocuspocusProviderWebsocket` + `provider.attach()`). Не создавать соединение на документ.
- Текст и задачи заметки на клиенте берутся из кэша `workspace.extract(id)`
  (пересчёт только после изменения заметки).
- Сервер (Hocuspocus `onStoreDocument`) сохраняет состояние в `yjs_documents`
  и пересчитывает производные таблицы: `notes_index` (plain_text, превью для списка),
  `tasks` (ключ — **note_id + id**: один и тот же id задачи может оказаться в двух
  заметках после копирования), `notes_index.deleted` (заметка в корзине — из документа
  пространства).
- Права проверяются в Hocuspocus `onAuthenticate` (JWT, share-токен + PIN для гостей).

### 3.2. Таблицы (черновик)

`users`, `sessions`, `settings`, `yjs_documents` (name, state BLOB, updated_at),
`note_versions` (note_id, state BLOB, author, created_at), `notes_index`,
`tasks`, `attachments`, `shares` (token, note_id, mode, password_hash, wrapped_key,
expires_at, revoked_at), `collab_invites` (token, note_id, pin_hash, guest_name,
failed_attempts, locked_until, expires_at, max_devices), `encrypted_notes`
(note_id, blob, version, kdf_params).

## 4. Дизайн

Макеты экспортированы в `design/` (открывать через `python3 -m http.server`):

- `design/Ничего не выбрано — экран приветствия-html/Main.dc.html` + PNG — главный экран;
- `design/Открыта заметка-html/Opened.dc.html` + PNG — открытая заметка.

Это **референс**, а не код: переносить значения (цвета, размеры, отступы, радиусы,
тени) в свои компоненты, а не копировать разметку.

### 4.1. Раскладка

Три панели на сером фоне, панели 2 и 3 — «парящие» белые карточки:

1. **Навигация** (~264 px, без карточки, прямо на фоне): лого, кнопка «Новая заметка»,
   разделы (Все / Задачи со счётчиком «N сегодня» / Общие), дерево записных книжек
   с подразделами (сворачивается, «+ Подраздел»), метки-таблетки. Внизу закреплены:
   Корзина, Настройки, блок профиля (аватар-инициалы, имя, статус синхронизации).
   Середина панели прокручивается, верх и низ — нет.
2. **Список заметок** (~368 px): заголовок (+ «хлебная крошка» книжки над ним),
   поиск, группы по датам. Дата — **скруглённый серый блок** («Сегодня … 15 ноября»).
   Заметка — две строки: название + время, одна строка описания. Без лишних значков
   (только замок у зашифрованных). Выбранная — мягкая заливка акцентом.
3. **Редактор** (остальное): сверху путь «Книжка / Подраздел», время изменения, кто
   редактирует, кнопки (история, пароль, «Поделиться», ещё, закрыть). Ниже —
   **парящая панель форматирования** по центру. Текст — колонка до 720 px.
   Если заметка не выбрана — **экран приветствия**: «Добрый вечер, <имя>»,
   кнопки «Новая заметка» / «Новый список задач», блок «На сегодня» (задачи со
   сроком сегодня и просроченные из всех заметок), подсказки хоткеев.

Экран всегда ровно по высоте окна, каждая панель прокручивается сама.
На мобильном (позже отдельный макет) — три экрана с переходами вместо трёх панелей.

## 5. Инфраструктура и деплой (схема владельца)

- Репозиторий: **GitHub `kozhevyatov/selfnote`** (публичный). Ветка `main`.
- **GitHub Actions** (`.github/workflows/docker.yml`): на каждый push в `main` и тег `v*` —
  typecheck, lint, unit- и интеграционные тесты, сборка; затем образ
  **`ghcr.io/kozhevyatov/selfnote`** (теги `latest`, `sha-…`, для релизов `X.Y.Z` и `X.Y`).
  Пулл-реквесты только проверяются, образ не публикуется. Платформа — `linux/amd64`.
  Красный CI = образ не публикуется: перед завершением задачи прогонять те же команды.
- Релиз: тег `vX.Y.Z` (`git tag v0.2.0 && git push --tags`).
- Сервер: Synology (Container Manager), папка `/volume2/docker/selfnote/`. **Исходники на
  NAS не нужны**:
  ```
  /volume2/docker/selfnote/
  ├─ docker-compose.yml    ← копия из репозитория (+ на NAS раскомментирована сеть db)
  ├─ .env                  ← настройки, пример — env.example (не в Git)
  └─ data/                 ← SQLite, вложения, jwt.key, database.json, бэкапы (не в Git)
  ```
- Обновление на NAS: `docker compose pull && docker compose up -d` (или «Проект → Действие
  → Собрать» в Container Manager). Деплой-скрипт в `/volume2/docker/deploy/` при желании
  делает то же по расписанию. **В репозиторий его не класть.**
- Сборка из исходников (разработка, проверка Dockerfile):
  `docker compose -f docker-compose.yml -f docker-compose.build.yml up -d --build`.
- `app/docker-entrypoint.sh`: стартует от root, отдаёт `data/` пользователю сервиса,
  проверяет запись (у общих папок Synology есть ACL) и сбрасывает права через `setpriv`.
  Если записать нельзя — запускает от root с предупреждением. `PUID`/`PGID` в `.env` —
  запуск от пользователя DSM. В журнале первая строка — `selfnote: запуск от …`.
- MariaDB владельца уже есть на NAS (хост `db`, внешняя Docker-сеть `db`). Отдельный
  контейнер БД не поднимать. В публичном `docker-compose.yml` сеть `db` закомментирована
  (у других пользователей её нет), по умолчанию — SQLite.
- Домен и HTTPS — через Nginx Proxy Manager, для `/collab` включить Websockets Support.
  Открывать сервис по HTTPS: без него не работают service worker (офлайн PWA) и
  WebCrypto (понадобится для шифрования).
- Внутренний порт приложения: **1339**.
- `README.md` — витрина проекта для GitHub (описание, возможности, установка).
  Подробные технические заметки и отчёты по этапам — в `docs/`
  (`docs/development.md`, `docs/changelog.md`), а не в README.

## 8. Этап 2 + история версий — ✅ сделано (подробности — `docs/changelog.md`)

Следующий по порядку — этап 6 (совместная работа) или 10 (мобильный макет), на выбор владельца.

Делать по пунктам, после каждого — `npm run typecheck`, `npm run lint`, `npm test`.

### 8.1. Корзина
- Автоочистка: заметки с `deletedAt` старше 30 дней удаляются навсегда. Делает **клиент**
  при старте/синке (удаляет из документа пространства), сервер по `notes_index.deleted`
  + дате дополнительно чистит `yjs_documents`, `tasks`, `note_versions`, неиспользуемые
  вложения (раз в сутки, таймер в процессе сервера).
- В корзине: «Восстановить», «Удалить навсегда», «Очистить корзину» (с подтверждением).

### 8.2. Серверный поиск
- `GET /api/search?q=` — MariaDB `FULLTEXT` по `notes_index.plain_text` (миграция с
  индексом), SQLite — FTS5 (виртуальная таблица + обновление в `saveDocument`).
  Исключать `deleted = 1` и чужие заметки.
- На клиенте: локальный MiniSearch остаётся основным (офлайн); серверный — дополнение,
  когда сеть есть (подсветка совпадения в строке списка).

### 8.3. Задачи
- Повторы: атрибут `repeat` у `taskItem` (RRULE: ежедневно, по будням, еженедельно в
  выбранные дни, ежемесячно). При отметке повторяющейся задачи — новая дата `due`,
  галочка снимается, в историю идёт `doneAt`.
- Во вкладке «Задачи» — перетаскивание для порядка внутри группы «Без срока».
- Быстрое добавление задачи с главного экрана (в заметку «Входящие» — создаётся сама).

### 8.4. Список заметок
- Перетаскивание заметки на книжку/подраздел в первой панели = перенос.
- Контекстное меню строки: закрепить, переместить, в корзину.

### 8.5. Оформление
- Тёмная тема (система / светлая / тёмная) и акцентный цвет (4 варианта из макета +
  свой) в «Настройках». Хранить на устройстве и в документе пространства.
- Все цвета — только через CSS-переменные из `styles.css`.

### 8.6. История версий
- Кнопка «История» в шапке заметки → боковая панель: версии по дням (время, автор).
- Просмотр версии только для чтения, переключатель «показать изменения» (дифф с текущей:
  добавленное — зелёный фон, удалённое — красный зачёркнутый).
- «Восстановить» = применить содержимое версии как новое изменение (через Yjs, чтобы
  синхронизировалось на все устройства) + создать версию «до восстановления».
- API: `GET /api/notes/:id/versions` (список без state), `GET /api/notes/:id/versions/:vid`
  (state base64). Проверка владельца.

**Критерии готовности:**
- Заметка в корзине 31 день → исчезает на всех устройствах и с сервера.
- Поиск находит слово из заметки, которой нет на этом устройстве (новая вкладка
  инкогнито до полной синхронизации).
- Повторяющаяся задача «по понедельникам» после отметки переезжает на следующий понедельник.
- Тёмная тема переключается без перезагрузки, контраст текста ≥ 4.5:1.
- Восстановление старой версии в одной вкладке сразу видно во второй; в истории
  появляются «до восстановления» и сама восстановленная версия.
- Интеграционный тест дополнен: поиск, очистка корзины, восстановление версии.

### 8.7. Этап 9 подробно: бэкапы, экспорт, импорт — ✅ сделано

Реализация отличается от плана в одном: формат бэкапа — ZIP (общий модуль `packages/shared/src/zip.ts`), а не tar.gz. Код: `apps/server/src/backup.ts`, `apps/web/src/transfer/`, `apps/web/src/DataSettings.tsx`. Подробности — `docs/changelog.md`.

Делать отдельным заходом после 8.1–8.6, но до того, как сервис станет основным местом заметок.

**Бэкап всей базы (для администратора):**
- Автоматический бэкап по расписанию (по умолчанию каждую ночь в 04:00 по времени
  сервера, настраивается в админке): всё, что нужно для полного восстановления.
  - SQLite — через backup API better-sqlite3 (не копировать файл во время записи);
  - MariaDB — логический дамп таблиц сервиса средствами Node (без внешнего `mysqldump`),
    формат — JSON Lines по таблицам, BLOB в base64;
  - плюс `data/attachments/`, `database.json` (пароль БД — по желанию, флажок), `jwt.key`.
- Один архив `selfnote-backup-YYYY-MM-DD_HHMM.tar.gz` в `data/backups/` (путь можно
  переопределить `BACKUP_DIR`, например на отдельную общую папку NAS через volume).
- Хранение: последние 7 ежедневных + 4 еженедельных + 6 ежемесячных, старые удалять.
- Админка → «Резервные копии»: список, «Создать сейчас», «Скачать», «Удалить»,
  статус последнего бэкапа (успех/ошибка, размер, время). Ошибка бэкапа — заметное
  предупреждение админу в интерфейсе.
- **Восстановление:** из архива в мастере первого запуска («Восстановить из резервной
  копии») или в админке с подтверждением (текущие данные сначала сами бэкапятся).
  Можно восстановить SQLite-бэкап в MariaDB и наоборот (переезд между БД).
- Версия схемы в архиве; при восстановлении старого бэкапа прогоняются миграции.
- Зашифрованные заметки попадают в бэкап как есть (зашифрованными).

**Экспорт для пользователя:**
- «Настройки → Экспорт»: все заметки или выбранная книжка.
- Формат **Markdown + картинки** (ZIP): папки = книжки/подразделы, файл = заметка,
  front matter (title, tags, pinned, created/updated, задачи со сроками), картинки в
  `attachments/`. Спойлер — `||текст||`, задачи — `- [ ] текст 📅 2026-11-20`.
- Формат **SelfNote (полный)**: JSON со структурой пространства + Yjs-состояния заметок +
  вложения — без потерь, для переноса между серверами/аккаунтами.
- Экспорт одной заметки: Markdown, PDF (через печать браузера).
- Зашифрованные заметки: экспортируются только после разблокировки, иначе — пропуск
  с пометкой в отчёте.

**Импорт:**
- Полный архив SelfNote (дубликаты по id — «пропустить / создать копию»).
- Папка/ZIP Markdown (Obsidian и т. п.): папки → книжки/подразделы, `- [ ]` → задачи,
  `![]()` → картинки, `#теги` → метки.
- **Synology Note Station `.nsx` — приоритет** (владелец переезжает с Note Station).
  `.nsx` — это ZIP: `config.json` со списком записных книжек и заметок, записи книжек и
  заметок в JSON (название, содержимое в HTML, книжка-родитель, метки, даты создания/
  изменения, ссылки на вложения), вложения отдельными файлами. Перенос:
  книжки → записные книжки, HTML → документ TipTap (через `generateJSON` + схема
  редактора), чек-листы → задачи, метки → метки, картинки → вложения (через обычную
  загрузку с EXIF strip), даты сохраняются. Заметки под паролем Note Station — пропуск
  с пометкой в отчёте. Прежде чем писать парсер, разобрать реальный экспорт владельца.
  Ориентиры по формату: github.com/Maboroshy/Note-Station-to-markdown,
  marph91.github.io/jimmy/formats/synology_note_station.
- Позже: Evernote `.enex`, Google Keep (Takeout), Apple Notes (через экспорт в файлы).
- Импорт идёт через Yjs-документы (как обычное создание заметок), чтобы всё сразу
  синхронизировалось на устройства. После импорта — отчёт: сколько заметок, задач,
  картинок, что пропущено и почему.

**Критерии готовности:**
- Ночной бэкап создаётся сам, лишние архивы удаляются по правилу хранения.
- Бэкап SQLite восстанавливается на чистом сервере с MariaDB (и наоборот): заметки,
  задачи, картинки, пользователи на месте, вход работает.
- Экспорт в Markdown открывается в Obsidian; импорт этого же архива в новый аккаунт
  даёт те же книжки, заметки, задачи со сроками и картинки.
- Интеграционный тест: бэкап → восстановление в новую папку данных → сравнение содержимого.

## 9. Правила работы

- **Не делай git commit / push / tag.** Коммитит и пушит владелец сам (SourceTree).
  Просто меняй файлы в рабочей папке.
- Отчёт о сделанном пиши в `docs/changelog.md` (новый раздел сверху), README не раздувай.
- Не клади деплой-скрипт в репозиторий (см. §5).
- Не добавляй отдельный контейнер MariaDB — используй существующую через сеть `db`.
- Строки интерфейса — на русском. Код, имена переменных — на английском.
- Каталог `design/` — только для чтения.
- Изменения схемы БД — только новой миграцией, рабочие данные не терять. Новые колонки —
  с `DEFAULT` или `NULL`: старые резервные копии восстанавливаются без них.
- Новые таблицы автоматически попадают в бэкап (дамп идёт по списку таблиц базы).
- После изменений в Docker-части напомни владельцу, что нужна пересборка.
- Если решение спорное или противоречит этому файлу — оставь заметку в README в
  разделе «Открытые вопросы», а не молча меняй архитектуру.
